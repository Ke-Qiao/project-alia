## 2. 首轮产品交付边界

首轮交付是 macOS Server 与 Pi 5 组成的实体交互系统，包含：

- 自然全双工语音：同时采集与播放、回声处理、说话轮次判断、自然插话、暂停和恢复策略。
- 可追踪的交互与工具执行：授权、确认、取消、独立执行事实、幂等与未知结果。
- 规范记忆、人格连续性、Affect / Regulation、受策略约束的主动语音和硬件表达。
- Pi 5 的实际播放回执、动作证据、本地安全约束、断连与重启处理。
- 面向开发和验收的 CLI / REST 操作入口、状态查询、日志与回放工具。

CLI / REST 必须能完成配置、设备绑定、记忆与人格管理、工具确认、主动策略控制和诊断，首轮不能依赖被搁置的前端完成这些流程。具体命令与接口随用例设计；不额外建设用户界面项目。

本轮不实现 Web Chat / 工作区、Web 与 Voice 双渠道产品体验、前端生成客户端或移动端构建验收。服务端仍维护准确的机器可读接口规范和协议版本，为后续接入提供稳定边界。

## 3. 目标架构与状态归属

保留 Rust 模块化单体、独立 Embedded 实时运行时、PostgreSQL/pgvector 和端侧 SQLite 的方向。模型运行时通过适配层接入；声学与模型依赖可以使用经过验证的外部库或独立进程，领域逻辑不绑定具体 GPU 后端。

| 模块 | 拥有的状态与职责 |
| --- | --- |
| `interaction` | Conversation、Turn、流式上下文、模型调用、轮次判断协调及取消 |
| `memory` | 规范记忆、证据、版本、删除失效、检索投影和 ContextPack |
| `companion` | 可出错的认知假设、Appraisal、Affect、Regulation、主动候选与机会判断 |
| `execution` | 工具定义、身份与权限检查、确认、EffectRun、幂等和外部执行核对 |
| `delivery` | 规范 Response、实体投递、播放与动作证据、输出资源仲裁 |
| `platform` | 身份/设备认证、配置生效、资源、数据库适配、健康与生命周期装配 |

模块只能直接写自己拥有的业务数据。跨模块原子用例使用明确的事务协调，不以多个独立提交冒充原子性。领域类型与 SeaORM、Tonic、模型 SDK 类型在适配边界转换。

Server 目标组织为 `src/modules/*`、`src/adapters`、`src/bootstrap`；Embedded 按 `audio`、`session`、`sensors`、`actuation`、`device` 分工。共享 crate 只承载真实共享的类型、策略、契约或测试工具，按依赖需要提取。目录组织必须与状态归属和调用关系一致。

统一四类生命周期：Turn、Response、Delivery、Effect。状态转移需要定义合法前置条件、终态、幂等行为和证据来源；具体枚举在契约设计中确定。不能把生成完成、网络发送成功、设备播放结束或机构到位合并为一种“成功”。

`turn_id`、`generation_epoch`、`response_id`、`playback_id`、`command_id`、`effect_id`、`device_boot_id` 等按场景组合。取消使旧生成失效，但不抹除已经发生的外部动作。无法核对的非幂等副作用进入 `unknown`，不盲目重试。

同事务 Outbox 负责业务提交与外部触发之间的间隙；业务执行事实独立于普通调试 trace。后台与前台分别限制模型并发、数据库使用、队列和超时。

### 3.1 逻辑角色与部署位置分离

2026-09-08 用户提出未来端侧模型、Server/Embedded 同机与 Rust 组合能力的设计问题。下面是纳入当前架构的工程建议；未来部署的具体实现/验收仍见台账 C04/C05，首轮实际目标仍是 macOS + Pi 5。

Server 和 Embedded 表示责任角色，不要求始终位于两台机器。模型运行位置也不由角色名称决定。设计覆盖以下演进形态：

| 形态 | 设备所在机器 | 另一台机器 | 实施定位 |
| --- | --- | --- | --- |
| 分离部署 | Device Runtime、音频处理与硬件安全 | Server、模型 Provider、业务存储 | 首轮 Mac + Pi 5 目标 |
| 设备侧推理 | Device Runtime + 部分模型，如轮次判断/STT | Server 的交互、记忆、工具与其他模型 | 目标设备运行后端和资源验收后采用 |
| 同机多进程 | Device Runtime、Server、模型进程和数据库均可在本机 | 可无另一台机器 | 未来一体设备的优先评估方案；单机仍有多个服务 |
| 同机组合进程 | 一个 Rust 启动入口组合 Server/Device 库 | 数据库和模型仍可为独立进程或外部服务 | 后续有明确交付/性能收益时评估，不等于单文件无依赖产品 |

端侧推理可先用常驻模型进程，适配器连接本机 endpoint；这已经把推理放到设备机器上，不要求立即把 Python/原生推理库嵌进 Rust 进程。部署决策除算力外，还要验证权重/算子/加速器兼容、内存带宽、散热、尾延迟和音频负载下的资源争用。

同机模式可先使用可配置的 loopback 连接，保留与跨机一致的认证、错误、取消和回执契约；必要时再增加受支持的 IPC 或进程内适配器。是否把模型、数据库也迁到本机属于单独的部署配置，不能把“两端同机”自动写成“全部离线”。

当前重构需要建立的边界：

1. **库与入口分开。** 应用核心提供可调用的装配、启动、停止接口；binary 负责配置、日志、运行时和生命周期。未来组合进程只组合库，不复制业务实现或重复初始化全局 runtime/logger。
2. **模型独立于位置。** TurnDetector / STT / LLM / TTS 的契约不暴露具体主机、Python对象或加速器；远端服务、本机服务与未来进程内后端遵循同一应用语义，保留各自真实能力和错误。
3. **状态所有者不复制。** Device Runtime 始终拥有实际音频时钟、播放游标和硬件安全；每个会话的规范轮次由唯一 Interaction 所有者决定。设备侧可以立即暂停并报告事实，不能因模型下沉再复制一套记忆、工具账本或规范轮次状态机。
4. **传输适配不改变契约。** 网络、回环或进程内路径都必须保留 turn/generation/boot/playback/effect 标识、背压、取消、权限和结果证据。进程内版本也不能绕过执行授权或静音约束。
5. **推理不阻塞实时音频。** 同机时继续隔离音频回调与模型执行的线程/进程和资源预算。单进程中的 Tokio task 不是崩溃隔离；采用单进程前验证原生依赖的故障影响。
6. **可配置部署先于动态迁移。** 初期在启动或受控切换时选择 Provider 和 endpoint。运行中跨机器迁移会话、自动算力调度与无缝模型迁移不是本轮范围；若以后需要，须设计状态交接和 epoch 失效。

验收设计要复用相同的行为用例验证各适配器。协议故障模拟、本地回环和可调用启动/停止接口可以在首轮验证；未实现的进程内传输或设备模型后端不能标为已支持。

### 3.2 Rust 的构建组合与运行时选择

Cargo workspace 与 library crate 用于共享实现和依赖；不同 binary 是装配入口。当前仓库已有 workspace 和两端 `lib.rs`，但这不代表现有 Server 已可直接嵌入任意宿主，需要在重构时收敛启动和全局状态。[Cargo workspace 文档](https://doc.rust-lang.org/cargo/reference/workspaces.html)

Cargo features 用于编译可选后端/依赖，例如 `inference-onnx`、`audio-alsa`（此处仅为建议名称）。features 会合并，应按可叠加能力设计；远端/本地 Provider 的实际选择用运行时配置。互斥的“服务器模式/嵌入模式/一体模式”优先由不同 binary 或装配配置表达。[Cargo features 文档](https://doc.rust-lang.org/cargo/reference/features.html)

`#[cfg(target_os = ...)]`、`target_arch` 和目标相关依赖控制平台代码进入构建；它们不检测运行时 GPU 是否可用，也不自动解决第三方模型兼容。[Rust 条件编译文档](https://doc.rust-lang.org/reference/conditional-compilation.html)

无可用后端或配置要求了未编译能力时，启动验证应明确失败或进入用户允许的降级状态，不能静默改变模型位置、外发音频或绕过权限。部署可组合性应由代码边界和测试保证，不能只靠增加 Cargo 开关宣称实现。

## 4. 自然全双工设计与 Easy-Turn 接入

### 4.1 参考核验边界

核验日期：2026-09-08。Easy-Turn 官方资料将其定义为声学与语言信息结合的轮次判断模型，输出 `complete`、`incomplete`、`backchannel`、`wait` 四类。其公开对比实验使用 NVIDIA RTX 4090，表中 Easy-Turn 平均推理延迟为 263 ms；这不是 Mac、Pi 或 Alia 端到端延迟证据。[官方仓库](https://github.com/ASLP-lab/Easy-Turn)

论文描述其研究目标与四类轮次语义；不能据此认为 AEC、音频传输、播放器取消和完整交互生命周期已经由该模型解决。[原论文](https://arxiv.org/abs/2509.23938)

官方推理入口按数据集音频调用模型。代码中的 streaming/chunk 参数及单次生成缓存不能证明已经提供跨音频块的增量推理；在线窗口、重评估频率和过期结果处理需要单独验证。[推理入口](https://github.com/ASLP-lab/Easy-Turn/blob/main/Easy_Turn/wenet/bin/recognize4llmasr.py)、[模型实现](https://github.com/ASLP-lab/Easy-Turn/blob/main/Easy_Turn/wenet/llm_asr/llmasr_model.py)

Easy-Turn 的安装和真实权重验证已进入执行阶段，结果单独记录，不预先宣布通过。其在 macOS CPU/Metal/MPS 和流式窗口推理中的可用性、代价需实际验证；用户明确当前部署在 Server，不评估 Pi 运行 Easy-Turn。正式接入要记录源码提交、权重版本、运行依赖和许可证。

### 4.2 工程接入建议

```text
Pi 5 麦克风
  → 带时间戳的有界采集缓冲
  → AEC / 降噪（输入实际播放参考流）
  → VAD / 本地停播与会话控制
  → 持续上传的有界音频流
  → Server 增量识别 / TurnDetector
  → Interaction 轮次策略
  → 上下文、模型与工具
  → 流式 TTS
  → Pi 5 有界播放队列与播放器
  → 播放参考流 + 实际播放回执
```

以上是目标数据流，不是现有实现说明。重点约束：

1. 采集和播放同时工作，不能等录完一句才开始上传。明确区分持续采集、增量转写、轮次判断和流式合成。
2. AEC 在能获得实际播放参考与采集时序的位置完成。优先验证 Pi 端或音频硬件已有 AEC；确定处理链后再选择软件库，避免无依据叠加多个回声消除器。
3. 控制与媒体分离优先级和背压。播放缓冲满、网络抖动、模型等待都不能阻止本地停播。保留有界的近期输入，避免插话开头丢失。
4. 快速声学响应与语义判断分层：可检测的近端语音先采取可恢复的暂停/衰减措施；完整语义结果再决定接话、继续等待或恢复。阈值、恢复点和抗抖策略必须用真机数据验证。
5. Easy-Turn 作为可替换 `TurnDetector` 候选；其输出是判断证据，由 Interaction 结合上下文和策略决定动作。`backchannel` 不能一律终止回答；`wait` 的暂停或结束含义需要结合表达和会话状态。
6. 当前 Easy-Turn 固定部署在 Server，Pi 保持实时音频与安全职责，不对 Pi 运行该模型做评估。模型未达标时重新评估运行后端或候选，不将“仅唤醒词打断”描述为自然全双工完成。
7. 明确检测器输入契约，允许其直接消费音频并产生转写/轮次结果，或与独立 STT 协作；不未经验证强加一个串行“STT 后才能判断”的路径，也不默认重算两次 ASR。
8. 模型超时或断连时保持安全、可解释的降级状态；恢复后拒绝旧 generation/boot 的音频和动作。降级能力不能代替发布时的全双工验收。

### 4.3 全双工必须覆盖的交互场景

| 场景 | 需要证明的行为 |
| --- | --- |
| 用户说到一半停顿 | 不因短暂停顿提前抢话，后续输入与原意正确关联 |
| 回答中用户说“嗯/对” | 判断附和与接管请求，避免无条件丢弃回答 |
| 疑似插话后确认只是附和 | 临时避让保留原播放与生成所有者；仅由覆盖最新近端语音的新鲜判断恢复，不重播已提交前缀 |
| 回答中用户直接补充或纠正 | 无需唤醒词即可接收，及时停播，保存插话开头并切换轮次 |
| 用户说“等一下/先停下” | 硬约束及时生效，不继续排队播放旧回答 |
| 明确暂停后用户说“继续” | 同一暂停、原回答和完整原权限仍有效时恢复；附和、静音或超时不能代替继续指令 |
| 扬声器自身声音或环境噪声 | 不形成持续自触发、自转写或自回答循环 |
| 双讲、远近变化和不同音量 | 记录误打断、漏打断与识别损失，不只演示安静近讲样例 |
| 连续插话、迟到片段和设备重启 | 旧生成不复活，取消与回执保持一致 |

验收分别测量：近端说话到本地响应、确认打断到声学停止、轮次判断耗时、用户停说到首音、误打断/漏打断、抢话、输入丢失、CPU/内存/温度和音频欠载。样本集、统计窗口及数值阈值在 P0/P1 基线后锁定。

原提案的确认打断后 p95 ≤ 100 ms、唤醒反馈 p95 ≤ 150 ms、固定条件首音 p95 ≤ 3 s 仍是候选目标；模型检测时间须另外报告。任何指标尚未实测，不宣称达标。

## 5. 平台策略与验证等级

以下是建议验证矩阵。macOS Server 与 Pi 5 是首轮实际交付目标；其他 Server 平台保持可移植设计并尽可能取得构建/测试证据。未取得原生运行证据的平台不标为正式支持。

| 目标 | 本轮计划证据 | 当前状态 |
| --- | --- | --- |
| 用户指定 macOS / 实际架构 | 全量 Server 构建、数据库/模型集成、Pi 联调、恢复、长时运行 | Mac 芯片/内存待确认；本次工作宿主报告 arm64，不据此认定部署机器相同 |
| macOS 另一 CPU 架构 | 工具链和依赖允许时构建；有原生环境再执行测试 | 待安排，单独报告 |
| Linux x86_64 Server | 有可用 runner 时原生构建、核心测试、PostgreSQL 和模拟设备测试 | 待建设 |
| Linux ARM64 Server | 构建检查；有原生环境时运行冒烟 | 固定 2f8797c 已在 ARM64 容器通过 Server 默认检查、161 项库测试和 119 项真实 PG 集成；后续提交另验，见平台记录 |
| Windows x86_64 Server | 有可用 runner 时原生构建、核心/协议测试、平台安全检查 | 待建设；路径、密钥 ACL、退出/子进程行为需验证 |
| Raspberry Pi 5 / 8 GB | 指定系统下完整音频、动作、断连、安全和资源验证 | 系统、外设与测试接入待确认 |
| 其他 Embedded 平台 | 见 D03 | 用户明确搁置 |

Server 核心不依赖 Pi 音频/硬件库或特定 GPU。平台差异集中于适配层，验证路径、信号退出、进程管理、密钥权限、发现服务和原生构建依赖。模型服务的加速后端与性能另行标注，Server 可移植不能自动等于全部模型可移植。

跨平台检查从早期开始，不能在最后才集中发现平台耦合。没有 runner 的检查如实记录未运行，不把跳过计为通过。

## 6. 阶段、依赖与通过门槛

| 阶段 | 工作内容 | 阶段出口 |
| --- | --- | --- |
| P0 设计与基线 | 冻结范围、状态机、数据归属、平台边界；确定硬件/模型；建立测试清单和已有能力分类；制定增量实现包 | 设计可评审，环境缺口明确，测试状态区分通过/失败/未运行 |
| P1 全双工可行性与契约 | 提前验证 Pi 音频/AEC、持续上传、Mac 轮次模型；确定媒体/控制协议、时钟、取消和回执；建立可运行原型与测量 | 目标环境有真实双讲和自然插话证据，关键预算可测，确定模型/音频路线；原型不等于产品完成 |
| P2 新服务端核心 | 重建 Interaction / Execution / Delivery，新 schema、事务、Outbox、配置/身份边界和 Memory 用例；补齐 CLI/REST 运维入口 | 完整交互链路通过真实数据库与模拟设备故障测试，执行事实与投递状态正确 |
| P3 实体陪伴闭环 | 将 P1 验证的音频链路产品化；完善 Memory、Companion、主动语音和动作；回放→shadow→真机投递 | 无前端也能完成首轮功能；记忆删除、静音、撤权、机会与回执一致；硬件安全可验证 |
| P4 组件与平台收敛 | 按需分别验收 Rig/rmcp/HA、持久任务/Temporal、观测和资源隔离；完成目标 Server 平台检查 | 选定组件有版本、契约和故障证据，旧路径退出；跨平台结果透明 |
| P5 发布验收 | 全新安装、重复启动、迁移失败恢复、版本化资源、真机性能和至少 24 小时混合负载；文档与台账收敛 | macOS + Pi 5 完整验收，关键故障不留未解释状态；全部搁置项仍可追踪 |

P1 的音频与模型验证优先，避免核心设计完成后才发现全双工目标无法在指定环境成立。P2 的数据/状态设计可以在稳定契约范围内并行。P4 的单项技术验证可提前穿插；不能在一次切换中同时替换语音协议、模型适配和任务运行时。

Easy-Turn、AEC 及必要流式 STT/TTS 验证是首轮目标的组成部分；不是可以无记录延期的附加项。具体第三方组件若不能满足门槛，需要提交替代方案或明确未完成项，不能用 mock 成功关闭真实验收。

## 7. 质量与提交要求

复用判断依据是正确性、职责归属、故障语义、可移植性、维护成本和测试证据。不能仅因文件大而重写，也不能仅因“已经存在”而保留。允许较大但职责完整的重构包。

必测故障包括：生成/播放中打断、延迟与乱序媒体、重复命令、动作已发生但回执丢失、数据库提交后进程退出、任务执行后崩溃、设备重启、权限在投递前撤回、删除记忆时后台仍运行、能力快照过期、模型/AEC失败、热配置应用失败。

数据库测试使用真实 PostgreSQL/pgvector，关键成功不能来自缺环境的静默跳过。设备模拟测试和纯策略回放提供可重复证据；自然全双工、动作安全和延迟最终由真机验收。检查的实际结果和尚未运行项目见构建记录；模拟或组件测试不替代真机验收。

提交由主 agent 统一处理，按文档决策、测试设施、契约/schema、业务模块、端侧实现、适配器和旧路径清理分成可审查的变更包。每包附范围、行为不变量、验证结果及后退方法；不改写原历史，不把缓存和本地状态混入提交。具体拆分服从审查清晰度，不以缩小 diff 为目标。

## 8. Subagent 构建分工

| 角色 | 实施责任与写入边界 |
| --- | --- |
| 主 agent | 架构决策、共享领域类型、Proto、数据库迁移编号、锁文件、跨模块事务协调、集成与正常提交 |
| Server subagent | 按包负责 Interaction / Execution / Memory / Companion / Delivery 内部实现及测试；共享契约变更先反馈主 agent |
| Embedded / Audio subagent | Pi 5 音频、AEC、轮次模型接入研究、控制优先级、播放回执和动作安全；不负责前端 |
| Validation subagent | 独立数据库和模拟设备故障验证、平台检查、回放、文档/搁置台账审查；与实现者交叉复核 |

每轮派工必须指定文件范围、依赖版本、输入/输出契约、行为不变量和验收命令。多个 agent 不同时修改共享 Proto、迁移或锁文件。真机结果缺失时，agent 不能以“代码已生成”代替完成。
