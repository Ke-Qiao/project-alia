# L09：固定核心归属与旧 Provider 清理

日期：2026-10-09。起点 `b9ff6e04075ae16bbc23ba6f904610d82f973c5b`，分支 `codex/architecture-refactor`。本轮承接 [10 月 8 日的分层重构](layering-2026-10-08.md)，处理 L09 固定核心及其契约归属；执行状态以 [本轮 checklist](checklists/l09-2026-10-09.md) 为准。**本文记录实现和验收范围；最终冻结输入、运行结果和提交见本文最终验证。**

## 本轮解决的问题

上一轮已把 Memory、Interaction 和 Bootstrap / Platform 的主要职责分开，但 Conversation、Cache、Router、Persona、Skills、Insights、Sensor 仍在 `providers`。这些对象大多是唯一的固定核心实现，却通过聚合 Provider trait、单产品工厂和生命周期接口暴露给用例。Insights 还同时拥有调度、Memory 模型业务和缓存审查，单纯移动目录不能解决其职责混合。

本轮将真实实现、值类型和用例契约一起移至所属领域。生产装配明确创建固定服务；真正用于输入输出隔离、设备采集或故障控制的接口继续保留。已有持久化和授权实现按原语义迁移，旧目录、旧名称与单产品工厂直接删除，不提供兼容 alias、转发门面、双写或第二条执行路径。

Conversation、Cache、Persona、Routing、Skills 的值类型随其 owner 迁移，Insights 的 `InsightTask / InsightStatus / InsightPhase` 归 Platform 的 Insights 调度模块。Sensor 的纯值、freshness policy、配置与 `SensorReadProvider` 从 registry 持久化实现中分开。`providers/adapter.rs` 不再声明或重导出这些固定核心契约。

生产 `ModuleRegistry` 持有具体服务的 `Arc`；Bootstrap 只克隆同一实例进入消费边界，不新建平行状态。API、CLI、工具、Companion、Interaction、ModuleContext、测试与 fixture 的路径一起迁移。原生命周期审计名和历史 metadata 字符串保持原值，例如 `database_conversation`、`db`、`multi_layer`、`created_by: "pipeline"`；这些数据不是旧入口或类型别名。

## 删除的抽象与保留的真实端口

本轮删除 `ConversationBackend`、`CacheBackend`、`RouterStrategy`、`PersonaProvider`、`SkillProvider`、`InsightStrategy` 及相应旧实现名称。`create_cache / create_skills / create_persona / create_router / create_insights` 单产品工厂删除，固定对象在 Bootstrap 明确构造。外部模型和设备能力仍使用已有适配契约，不因这次清理增加新依赖或可配置替换点。

保留的端口有实际调用边界：

| 端口 | 保留原因 | 权限范围 |
| --- | --- | --- |
| `ConversationStore` | Interaction、Companion、CLI 消费会话行为；现有来源和提交故障测试需要可控实现 | 仅 `Send + Sync` 和 9 个必需的会话 / 事件操作，不继承生命周期 |
| `CacheStore` | 用例进行缓存读写、审查和 CAS；现有阻塞、取消与审批确认测试需要控制存储边界 | 仅 `Send + Sync` 和缓存操作，不允许消费方启动或停止服务 |
| `SensorReadProvider` | 设备或插件确有不同的按需采集实现 | 按 source 注册并读取指定传感器；注册、持久化与 freshness 决策仍归 SensorRegistry |
| 现有 `LlmAdapter / EmbeddingAdapter / SttAdapter / TtsAdapter` | 模型和音频能力仍有实际外部实现 | 保持现有能力、取消和资源约束，没有新增替换机制 |

`ConversationStore` 的 9 项方法全部要求实现。旧 trait 中 `append_event` 的默认静默成功、规范提交与来源写入的默认不支持分支被移除；真实服务原行为保留，测试替身必须明确说明支持或拒绝的操作。这避免新增替身忘记实现事件记录时被默认成功掩盖。

`InteractionServices` 只在 Conversation / Cache 的真实用例边界持有窄端口，Skills、Persona 和 Router 直接使用固定服务。Insights 从 ModuleContext 获取 canonical `Arc<CacheService>` 后，仅在 review 边界转换为 `Arc<dyn CacheStore>`，底层仍是同一个实例。

## Router 的必需构造

`RouterService::new(config, minor_llm) -> anyhow::Result<Self>` 显式接收原有 timeout、minor / major 开关和已经初始化的 minor LLM。原 `init` 中的参数读取与校验移入构造，Bootstrap 在原 Router 初始化阶段完成创建。Router 不再接受宽 `ModuleContext`，也不再存在构造成功但尚无配置的状态。

minor 与 major 同时关闭仍被拒绝。运行时设置仍在同一 RwLock 下构建候选配置，先校验再整体替换，非法更新不会部分写入 timeout。现有分类超时、解析错误 fallback、minor-only / major-only / 双模型提示、升级提示、候选白名单、去重及数量上限保持。

原 `PassthroughRouter`、测试专用 `DirectRouter` 删除。相关用例测试使用真实 RouterService 的现有 major-only 配置且不提供 minor LLM，因此不调用模型分类；实际回答继续由测试 LLM 产生。

`RouteDecision::CacheHit { response }` 没有生产构造者，也不携带规范缓存身份，故删除该不可达 variant 及对应 Generation / debug 分支。真正的缓存命中仍经 CacheService、Context source lineage 和原规范完成出口，不减少真实缓存能力。

## Memory maintenance 与无实例 capture 入口

Memory 维护现在拥有自己的输入与结果，独立执行提取、整固、反思、习惯推导。业务函数不接收 ModuleRegistry、AppState 或 Interaction 持久化对象。平台只负责决定何时、为哪个账户启动哪种维护阶段，并记录结果。

四条维护路径继续按以下顺序执行：

1. 从 Memory 取得原始写入快照和持久政策版本，按自动采集或维护用途检查政策。
2. 选择实际来源，materialize canonical rows，生成包含来源身份、revision 和 epoch 的 Context lease。
3. 将写入上下文绑定到该 lease，模型请求前再校验权限；提示词从已经验证的 canonical rows 构造。
4. 校验模型返回的目标、内容和敏感数据，将整固计划作为一个 guarded batch 提交；模型后的权限与来源校验仍在实际写入事务内执行。

`ContextService::materialize_memory_capture` 改为 `materialize_memory_capture(db, snapshot, origin)` 关联函数。该操作原本只使用 ContextService 的数据库字段，不使用 embedding；因此移除原维护路径中为调用它而构造的四个 `NoopEmbedding` 和临时 ContextService。这里“无实例依赖”只描述调用接口，操作仍会持久化 Context，并不是无状态存储。

事务隔离级别、数据库 statement timeout、账户与来源锁、政策校验、canonical payload、source revisions、提交确认和 `CommitUnknown` 错误体保持。新签名不添加额外查询、模型调用或替代授权路径。Context、Memory、Conversation、Delivery 的进一步跨表事务责任仍留待 L11。

## Insights 准入、期限与生命周期

Insights 的单一具体服务使用 `InsightService::new(enabled)`。保留原禁用状态与 feature 缺失的公开行为：

| 状态 | 行为 |
| --- | --- |
| 构造时政策禁用 | `name="noop"`，health Healthy；init/start/stop 不接入 DB、模型、scheduler 或 worker |
| 构造时政策禁用后的 schedule / trigger | 返回成功且不执行；包括无效 phase，保持原 Noop 行为 |
| 禁用时 status / 条件 / hot settings | status 为 disabled、无历史、pending=0；条件为空，set_conditions 不保存，hot settings 不消费键 |
| 请求启用，但未编译 `insights` feature | 构造返回原错误 `enabled insights require feature 'insights'` |
| 已启用服务的正常初始化 | 使用原政策和配置；未初始化、非法 phase、stopping、模型或存储失败继续传播原错误 |
| 已启用服务的 hot settings | 仅更新原有四个 prompt 键，不热启用 worker，不新增启用开关 |

本轮使用 `cfg!(feature = "insights")` 保持构造准入，服务体本身可在无该 feature 时编译，不再维护另一份 Noop 产品实现。该 feature 原来没有依赖项；这里没有声称保留原条件模块的二进制裁剪形态，也没有新增 feature。

平台仍把 Insights 登记为 `ShutdownPhase::Producers`，保留先注册 cron、再由 OwnedBackground 启动事件与 idle worker 的顺序。停止时先请求取消并等待所属 worker，再清理 scheduler task；错误聚合和任务身份保留，不生成游离后台任务。

30 秒 phase 预算仍包括等待并发 permit、授权读取和 provider 工作。Cache 审批已确认后，embedding 请求仍由当前阶段持有；期限取消只结束未确认工作，不重放已确认审批。日志自身保留独立的有界确认期限，错误继续明确说明先前更改可能已经提交。Memory 与 Cache 不被错误地包装成一个虚构的跨域原子事务。

## Persona、Skills 与 Sensor 的保留边界

Persona 的有效选择、用户覆盖、名称清理、模板渲染和失败回退保持；原 trait 的 `render_system_prompt` 默认业务也成为明确固有方法，没有丢失调用行为。

Skills 的插件注册 / 卸载仍包含原持久化、外部依赖检查和运行索引 reload。preferred tools 只贡献上下文与排序，不授予工具可见性，也不能跳过 Execution 的权限。**`api/skills.rs` 的 HTTP 创建、更新、删除后触发 reload 的现存 TODO 尚未解决**；不能把本轮保留插件路径的 reload 表述为所有 Skills HTTP CRUD 均支持热加载。

SensorRegistry 保留 owner 校验、source 命名、quality 处理、时间戳、新鲜度与 stale 策略、数据库和已有内存 fallback、按 source 的读取 provider 及 owned cleanup。目录与值类型拆分不引入新硬件采集，也没有启动实际设备、播放或动作。
