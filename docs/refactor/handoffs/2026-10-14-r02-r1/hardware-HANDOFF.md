## 结论与进度

当前公开资料明确描述 **R1 的 USB 采集输出**和**外部功放输出进入 R1 的 AEC 参考输入**。USB 接到 Pi 只证明目标连接方式；它不证明扬声器参考已进入硬件 AEC。主机软件 post-mix reference 同样不能代替这条物理参考路径。

公开介绍没有确认 USB playback endpoint 或 USB 播放到内部 AEC 的路由；这表示**本轮未证实**，不表示该功能必然不存在。外部参考引脚已明确，但输入额定值、具体功放兼容性、实物/固件与模式仍缺依据。因此本轮不把任何输出设备、功放或接法判为已兼容，也不据此新增主机软件 AEC。

## 对后续 R02 的约束与待补信息

1. **先形成硬件 AEC 的可验证路径。** 依据目前公开材料，待核对的拓扑为 Pi 播放输出 → DAC/功放 → 扬声器，并从厂商认可的位置把功放输出参考接到 R1；R1 经 USB 把处理后 capture 送回 Pi。该拓扑是资料支持的候选，电气未确认前不能当作接线授权或兼容方案。主机 mixer 负责合成与精确取消，R1 AEC 消费真实参考，两者职责不同。
2. **缺口是输出链与厂商额定，不再重问连接主机。** R1 尚未接入、计划 USB 接 Pi 5 已由用户确认；需要的是实物/固件标识、对应厂商附件、最终功放/扬声器型号，以及参考端对这些输出的允许接法。Root 集中收集这些信息；本分工没有联系厂商或代选未经核对的硬件。
3. **接入后先只读枚举，再决定测试。** 复用既有[只读顺序](../2026-10-14-hardware-confirmation/audio-HANDOFF.md)：稳定 USB 身份、`/proc/asound` capture/playback 描述和账户权限分开记录，包含 stderr。枚举发现没有 playback endpoint 才能作为该实物/固件的证据；当前文档缺少说明不能代替枚举。串口或固件工具的查询性质未明确前不执行。
4. **模式确认后再决定 consumer。** 若采用 R1 硬件 AEC，应记录实际处理输出与参考来源，不能把主机软件旁路命名成软件 AEC。若之后确有软件 AEC 需求，再据选定 consumer 确定帧长、格式、参考缺口与独立时钟处理；现有固定 reference block 大小不是 AEC 帧需求，本轮不引入处理器或重采样估算器。
5. **保留现场未知。** 同主机不证明采播共享时钟；AEC 支持不证明参考接通；输出流提交/软件取消也不证明物理扬声器停止或声学收敛。这些须在后续明确的录放音窗口中留证，不能用离线合成测试替代。
