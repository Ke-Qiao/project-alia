## 已核对的当前事实

1. 提案第 10 节区分随发布的可信 Rust 扩展、外部 MCP／API 和未来不可信隔离代码；明确本机 stdio 是程序执行，清空环境不是沙箱。现有 Execution 的 effect、参数、用户、工具实现／目录版本与批准期限是可复用的业务边界，模型 tool calling 和工具说明均不是授权。
2. `expression/abi.rs` 的 JSON 子进程实现直接运行 manifest 中的 command／working_dir；`ExpressionPluginSandbox` 只控制清空及追加环境。`wait_with_output` 在退出前收集 stdout／stderr，`max_stderr_bytes` 只影响事后预览；没有据此得到输出内存、文件、网络或进程树隔离保证。`kill_on_drop` 和 timeout 不证明全部后代已退出或原资源已回收。此路径只能按受信本机命令理解，不能直接作为未经审查代码 runner。
3. `ExternalExpressionPlugin::provenance_pin` 缺省为 None，JSON 命令实现没有覆盖该方法。当前私有 appraisal 路径检查持久 policy 中的 pin，并要求取消配置／不输出原始 stderr，因而不能说任意 JSON 插件已通过 appraisal 来源门。intent／plan／safety 三条规划路径是另一契约：它们直接收到 `ExpressionInput`，而 `plan_for_generation` 会填入全部 materialized memory。对当前受信配置的设计不等于未来不可信插件可以默认获这些私密输入。
4. 表达外部 safety hook 后仍执行内置 `apply_builtin_safety_policy` 和计划校验。这个宿主底线必须保留；第三方可提交候选或收紧建议，不能成为批准本身，不能替换用户政策、Context 根校验、Execution 或 Body 门槛。
5. `CompiledToolPlugin` 的 `PluginToolContext` 含注册表和命名空间 storage，Rust 代码在宿主进程内执行；受限对象接口不是对恶意 native 代码的内存／OS 隔离。`StorageScope::User/Channel/Conversation` 可由调用者填写 owner 字符串，当前 namespace／scope 类型检查不能直接当作未来不可信调用者的用户授权验证。
6. Server `/plugins` 当前为注册工件／存储管理；Embedded 有已认证的 PluginManager 安装、启动、停止 RPC，协议 success 字段也不证明隔离强度或实际清理完成。本次只核其入口，不把它与未来 Server 第三方包系统混成已验收的统一插件平台，也不扩展到 Embedded 实机。

上述为静态范围差异，不是本轮新做了攻击复现。未经审查代码的默认隔离模式以实际隔离与授权为新 runner 的进入门槛；用户另已确认管理员单独授予宿主信任的本机模式，该模式不享有不可信代码隔离保证。两种模式不自动互相降级，本轮不顺带修旧生产路径。

## 最小完整契约建议

| 层 | 宿主记录／决定 | 不能推出的结论 |
| --- | --- | --- |
| 包来源 | 下载／导入来源、声明发布者、可选签名及其信任链／状态、审核状态、安装操作者 | 签名有效只证明对应身份对内容的声明，不证明代码无恶意；允许明确标记的未审核／未签名包进入安装但默认停用 |
| 内容身份 | 宿主计算不可变包摘要，覆盖 manifest、可执行内容和运行必需资产／依赖；另绑定 ABI、运行后端、入口和配置 revision | 名称／版本／远端 URL／作者提供的摘要不等于实际执行字节；同名覆盖或可变依赖不能继续使用旧 grant |
| Grant | 用户／管理员向具体安装实例和内容身份授予能力、数据范围、资源上限及有效期，宿主保存可撤销 revision | manifest 只是请求；安装确认、发布者签名、工具自称 read-only 都不自动产生授权 |
| 运行隔离 | 默认隔离模式在运行前证明能实施对应文件、网络、进程、CPU／内存／输出和宿主调用限制；不满足则该模式不可启用。独立受信本机模式须管理员另授宿主信任 | 清环境、单独进程、容器名称或编译到 WASM 都不是完整验收证明；不得静默退回宿主 native 执行；受信本机模式不能冒称同等隔离 |
| Effect approval | 复用 Execution，对具体用户、参数、目标、工具／包版本和当前政策作必要批准及分派复验，保留 effect／unknown | 一次启用 grant 不等于批准将来每个外部副作用；返回 success 不是宿主已核实外部效果 |

数据最小化和当前政策贯穿这五层，不再另建平行的记忆、审批或动作系统。运行能力是“包请求 ∩ 当前 grant ∩ 宿主政策 ∩ 后端可实施能力”；任一缺失即拒绝相应能力。

### 安装与升级

- 安装只验证和保存数据，不执行安装脚本、导入模块、探测 hook 或 health hook；包括解包前后大小／条目数限制、规范路径和符号链接／硬链接逃逸拒绝。具体包格式随实现确定，不预建市场。
- 安装记录与启用记录独立。未审核身份可以安装；默认隔离模式只有所需隔离和明确 grant 已满足才运行。管理员可单独明确授予绑定内容身份的受信本机模式，它不具有不可信代码隔离保证，不能由隔离失败自动转入。不能把“允许安装未经审核代码”翻译成“用户必须先人工审核每行代码”。
- 摘要覆盖实际运行内容，配置权限与运行后端有独立 revision。包更新、入口／依赖改变不继承旧内容授权；权限扩大需新 grant。迁移或清理 hook 本身也是受限执行，不能因处于安装／卸载阶段获得宿主全权。
- 更新先封闭旧版本新调用；已认领调用保留原 executor／内容与 completion。新版本不得冒领旧批准或已执行 effect。停止／卸载请求和实际 quiescent 分开记录；未结束则保留 owner、原始失败和待清理状态。

### 运行与数据

- 未授予能力默认没有文件系统、网络、任意进程、环境秘密、原始数据库或宿主注册表。运行目录不是权限边界；文件读写由明确根目录或宿主对象句柄授权，不能让插件自己选择 owner 身份来扩大范围。
- 宿主 broker 应绑定 plugin instance、content、grant revision、调用用户／会话和 Context 根。每次敏感读取／副作用分派复验当前政策，结果与派生数据保留必要来源，不能由插件伪造 current actor 或根。
- 私密文本、Memory、Affect 不因插件选择 planner 能力就全量附送。按具体能力请求最少字段；有私密输入又有网络外发时需明确组合范围。撤销能阻止后续宿主读取／调用并清理受控副本，不承诺追回第三方已经看到或已发送出去的数据。
- 网络能力不能退化为任意 socket／同域任意 HTTP 即被视作只读：端点、方法、目标和请求数据边界由宿主决定；会产生外部效果的 broker 调用仍经 Execution。凭据由受控引用在 broker 注入，不原样下发插件；不能因工具描述写了 read-only 就省略风险分类。
- CPU／内存、实例／调用并发、队列、输入输出／日志、wall deadline、存储总量和请求额度都有宿主上界，manifest 只能请求更小或待批准的额度。输出在读取阶段限额；日志默认脱敏，不把全量 stderr 或私密输入写入证据。
- 取消、硬终止、原 completion 与资源回收是不同事实。后代进程和持久 host 操作需明确 owner；未取得完成见证时不报告 stopped／uninstalled 成功。已发送外部效果按原 Execution 规则保存 unknown，不因取消自动重放。

### 语言与协议分工

受信编译期 Rust 接口、MCP／服务 API、不可信隔离 ABI 可以共享工件登记和 Execution，却不必伪装为同一种执行机制。MCP 解决协议互通，本地 MCP 子进程遵循相同执行模式：默认隔离，受信本机须管理员单独授予宿主信任且不享有隔离保证；远端 MCP 的数据披露和服务信任需单独说明。隔离后端可由 Root 按官方能力和目标平台决策，本轮不新增依赖，不把候选运行时写成已支持。

## 后续实现的有限验收门槛

以一个无权限纯计算包、一个明确 grant 的 broker 工具和恶意夹具覆盖下列类别即可形成首个出口，不穷举全系统故障：

1. 安装不执行代码；包路径逃逸／超量／内容变化拒绝；未审核身份始终可见。
2. 无 grant 时文件／网络／进程／秘密／跨 owner 数据均不可访问；越权 broker 参数拒绝，工具描述不能批准自己。
3. 更新、撤权与在途调用竞争：旧内容不能拿新身份，旧批准不授新包，原 effect 与 completion 不丢失。
4. 恶意无限循环、输出洪水、内存增长、异常退出／后代占用被有界处理；记录原失败和真实清理状态，不只检查调用 future 返回。
5. 私密输入最小化、来源失效、日志脱敏和存储保留／卸载政策可观察；不把普通读接口的 scope 字符串校验当成当前用户授权。
6. 第三方 planner／tool 不能替代内置安全政策或直接写核心 Memory／Context／Response／Execution 表；副作用仍有相同批准与 unknown 语义。

以上是未来实施出口，不是本轮已通过数。Root 收到用户集中确认并形成规范后再交叉审查，最终只对规范完整性给出 GO／阻断。
