# Durable Execution API

Execution records an intention and its authorization before invoking a tool. The
HTTP response is a durable ledger acknowledgement. Only an effect whose `status`
is `succeeded` has a successful adapter receipt; HTTP 200, approval, dispatch, and
elapsed time do not establish success.

The generated OpenAPI document includes these routes, request schemas, effect
states, confirmation payload, and typed domain errors. All routes require the
normal authenticated bearer token. The authenticated account owns the effect;
request bodies cannot choose a different owner.

## Propose and inspect

```http
POST /api/v1/tools/execute
Authorization: Bearer <token>
Content-Type: application/json

{
  "request_id": "86a6581b-c326-4807-9332-45c6242d2766",
  "tool_name": "get_current_time",
  "arguments": {"format": "iso8601"},
  "call_id": "optional-correlation-label"
}
```

`request_id` is a required, non-nil UUID generated by the caller. Keep it for
retransmissions of the same operation. The REST route uses invocation key `0`;
the unique execution identity is `(authenticated user, request_id, invocation_key)`.
`call_id` is a correlation label, defaults to the request UUID, and does not change
that identity. Arguments must be a JSON object of at most 16 KiB encoded. Unknown
request fields are rejected.

An identical retry returns the existing `effect_id` and current fact. Changing
arguments, tool or approval/version inputs under the same identity returns
`409 idempotency_conflict`. A new UUID denotes a new intention and can execute the
action again. Retrying an `unknown` effect with its original identity returns
`unknown` without dispatching again.

Use `GET /api/v1/effects/{effect_id}` for the current record. Use
`GET /api/v1/effects?limit=25&before=<effect_id>` to list the owner's records,
ordered by `created_at DESC, effect_id DESC`. The exclusive `before` cursor is the
last effect from the preceding page. Page size must be positive and is capped at
100. An unknown cursor or one not owned by this account yields an empty page and
does not expose another owner's records. A single-effect read returns 404 for both an absent effect and an
effect owned by another account.

The record includes `key`, `tool_name`, `arguments`, immutable intent/tool/policy
and catalog digests, approval facts, dispatch claim identity/deadline, timestamps,
and optional `completion`. Clients should retain `effect_id`, `request_id`, and
`intent_digest` for inspection and consent. A retry can use a new correlation
label, while the stored record retains its original `model_call_id`.

Trusted `source_privacy_epoch`, `source_received_at` and optional `source_event_id`
are stored with the effect and restored unchanged in its worker context. They
cannot be set through this request body. Retransmission preserves the original
source; its epoch and message ID are part of the immutable intent. Missing epoch
does not mean the current version. Memory tools require an admitted source epoch;
AI memory writes also require a committed user message and revalidate its owner,
stored source epoch and original audit time. The epoch, rather than a comparison
between Server and database wall clocks, establishes the deletion boundary. See
[source admission](source-admission.md) for the ingress and queue contract.

## Confirmation and cancellation

A `proposed` effect with `requires_confirmation: true` requires owner confirmation.
Display the actual tool and arguments from that record, then submit the exact
digest the owner reviewed:

```http
POST /api/v1/effects/<effect_id>/confirm
Authorization: Bearer <token>
Content-Type: application/json

{"intent_digest": "<digest returned in the effect>"}
```

Only this authenticated owner endpoint supplies explicit approval. A model tool
argument such as `{"confirmed":true}` has no approval authority. Repeating a
matching confirmation is idempotent where the transition permits it. Authorization,
database-owned catalog policy, and approved versions are checked again before
claim. Approval is valid for 15 minutes; expiry or a version change before dispatch
prevents execution and requires review of a new intention.

`POST /api/v1/effects/<effect_id>/cancel` cancels a proposed/approved effect.
Repeating cancellation of an already cancelled effect is accepted. A dispatched or
completed effect cannot be made unexecuted; cancellation returns a transition
conflict. This endpoint does not claim to reverse external side effects.

## State and evidence

| State | Meaning | Client behavior |
|---|---|---|
| `proposed` | Intention stored but not approved. | If `requires_confirmation` is true, obtain owner consent. Otherwise an automatic approval may be awaiting capacity; retry only the same request identity. |
| `approved` | Authorized and queued for bounded dispatch. | Poll the same effect; do not claim completion. |
| `dispatched` | A worker committed an exclusive claim before invoking the pinned adapter. | Poll; transport loss does not authorize another invocation. |
| `succeeded` | Adapter success and its receipt were durably stored. | Use `completion.receipt` as the available evidence. |
| `failed` | Definitive failure evidence, or rejection before external execution. | Inspect `completion.evidence`; a new attempt is a new intention. |
| `unknown` | External outcome is unverified. | Inspect/reconcile externally; do not automatically retry the action. |
| `cancelled` | Cancellation committed before dispatch. | Treat as not dispatched by this effect. |

`Completion` is tagged with `status` and contains `receipt`, `evidence`, or `reason`.
An adapter exception, panic, deadline, oversized receipt, or a legacy false result
without definitive non-execution evidence becomes `unknown`. Only adapters that
explicitly supply definitive failure evidence may turn a false result into
`failed`. These receipts describe the adapter's evidence; they do not add device
presentation, hardware-clock, or other facts the adapter has not observed.

The server owns four concurrent workers. Calls use the configured tool deadline,
clamped to 1–300 seconds. Terminal effects leave the dispatch outbox. An expired
`dispatched` lease becomes `unknown` after a 10-second recovery grace and is never
re-enqueued. Receipt persistence may retry the same receipt three times, with a
2-second database deadline per attempt; it never repeats the external executor.
Persistence failures are reflected in service health and returned by shutdown.

## Implementation identity and hot replacement

A code-backed tool must provide a nonempty `implementation_revision`; the raw
registry must supply a nonempty `registration_revision`. The stored tool digest
includes both revisions, the server build digest, schema, source, and authorization
metadata. Even a replacement with the same JSON schema invalidates an unclaimed
approval through its registration revision.

Catalog mutation and claim are serialized. After claim, the worker retains the
resolved executor `Arc`: replacing the registered tool affects later claims, not
that invocation. Adapter authors must update their implementation revision for
behavior changes and must not hide a different implementation behind an unchanged,
mutable revision. The public execution registry does not expose raw executor
resolution as an execution bypass.

## Shutdown and retry boundaries

The synchronous tool result wait has a 10-second budget, including database polls
and cancellation acknowledgements. If no fresh acknowledgement is available it
returns the last observed effect fact, without asserting successful cancellation
or repeating the executor. Use the effect query endpoint for subsequent evidence.

Submission has one 5-second deadline covering catalog access, proposal and automatic
approval. An elapsed deadline returns HTTP 503 (`execution_unavailable`); it does not
prove that a database commit failed. Once an automatic session effect is registered,
an approval error, timeout or dropped submit waiter cancels its originating session
token and retains the cancellation mapping until a durable cancellation or a claim
resolves ownership. This also covers a committed approval whose acknowledgement was
lost. Inspect the effect using the original request identity; do not invent a new
request to retry an uncertain action.

Each shutdown call has one 10-second budget covering admission, cancellation writes
and the worker join. It first cancels all known session tokens, then waits for
in-flight admissions to finish registering ownership and snapshots again. At most
eight cancellation writes run concurrently, each with a 2-second database deadline.
Automatically approved session requests cannot intentionally carry forward as stale
voice actions. A cancellation or join that exceeds the budget returns an unhealthy
shutdown result with unconfirmed effect IDs and admission/worker pending flags. The
server cannot assert a cancellation it could not commit. Unconfirmed mappings remain
available for a subsequent shutdown attempt; the original failure remains visible.

REST and scheduler requests without session cancellation ownership remain durable
and may proceed after restart if approval, versions and authorization are still
valid. Unapproved proposals remain available for later explicit owner review.
Already dispatched calls retain their executor until completion or the configured
execution deadline. Exceeding a shutdown budget does not abort a dispatched call or
stop its underlying adapters. Dropping one shutdown waiter does not lose the stored
worker handle; a later shutdown call can still wait for its result. This bounded
service return is not a guarantee that an uncooperative native task or its host
runtime can be killed safely.

Domain errors use this envelope:

```json
{"error":{"code":"idempotency_conflict","message":"idempotency key belongs to a different intent"}}
```

| HTTP | Execution error codes |
|---|---|
| 400 | `invalid_input` (also malformed JSON/query/path input) |
| 403 | `identity_unlinked`, `unauthorized` |
| 404 | `not_found` |
| 409 | `idempotency_conflict`, `version_changed`, `invalid_transition`, `completion_conflict` |
| 429 | `capacity_exceeded` |
| 503 | `execution_unavailable` |

Authentication errors use the server's normal authentication envelope and HTTP 401.
Database internals are not exposed in 503 responses. If acknowledgement is lost,
query the known effect, or repeat the exact payload with the same `request_id`.
Do not generate a new request identity to work around a timeout, unknown result,
capacity error or idempotency conflict.

## Validation

`tests/execution_service.rs` uses the production service/registry/repository and
real PostgreSQL, with a fresh schema per case and fake external adapters. It covers
retransmission, owner confirmation, bounded concurrency, session cancellation,
missing revisions, same-schema replacement before claim, executor pinning after
claim, unknown outcomes without retries, and receipt/cancellation write failures.
OpenAPI and error-envelope tests validate the machine-visible contract separately.
No hardware or external-effect delivery is inferred from these tests.
