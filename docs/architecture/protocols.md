# Protocols

Project Alia uses different protocols for different latency, ownership, and
deployment boundaries.

## Frontend to Server

The frontend talks to `alia-server` over HTTP and WebSocket.

- REST APIs live under `/api/v1`.
- `/health` is available outside the API prefix.
- WebSocket is used for live UI-facing server events where appropriate.
- OpenAPI/Scalar support is generated by the server for API inspection.

Current API areas include auth, users, devices, voice, conversations, plugins,
rules, scheduler, settings, sensors, memories, personas, insights, skills,
tools, and channels.

## Local Discovery

Discovery deliberately uses separate service identities for the control plane
and embedded edge nodes:

| Advertiser | Service | Purpose |
| --- | --- | --- |
| `alia-server` | `_alia-server._tcp` | LAN discovery of the HTTP control-plane endpoint. |
| `alia-embedded` | `_alia-embedded._tcp` | Discovery and binding of edge devices over gRPC. |
| `alia-embedded` | BLE service `3d4d5f9a-d0b9-4a7f-9f47-9d6cc7b5b4f1` | Auxiliary provisioning beacon and GATT Wi-Fi setup for nearby mobile clients. |

The server mDNS record includes `schema=alia.server.discovery.v1`,
`kind=alia-server`, `mode`, `endpoint`, and common API paths. Embedded discovery
remains owned by the embedded channel and is surfaced to the frontend through
device APIs such as `GET /api/v1/device`.

Embedded BLE provisioning uses the same service UUID for GATT. The network
status characteristic is `3d4d5f9a-d0b9-4a7f-9f47-9d6cc7b5b4f2`; the network
config write characteristic is `3d4d5f9a-d0b9-4a7f-9f47-9d6cc7b5b4f3` and
accepts JSON Wi-Fi credentials. The embedded node applies Wi-Fi through the OS
network manager, not through Alia config files.

## Server to Embedded

Server and embedded communicate over gRPC using protobufs in `crates/proto`.
The same proto crate is used by both Rust codebases through the workspace.

Important services:

| Service | Hosted by | Purpose |
| --- | --- | --- |
| `alia.audio.AudioStream` | Embedded | Server-to-device audio playback, playback stop, direct-response action cues, and bidirectional audio hooks. |
| `alia.audio.ServerAudioIngress` | Server | Embedded-to-server captured audio upload and active turn interruption. |
| `alia.settings.EmbeddedSettings` | Embedded | Settings snapshot, volume, and direct response management. |
| `alia.sensor.EmbeddedSensor` | Embedded | Sensor discovery, reads, and optional sensor commands. |
| Binding/plugin services | Embedded | Device binding and embedded plugin support. |

## Audio Control Paths

Audio and control are intentionally separate:

- Captured speech is uploaded to the server audio ingress.
- TTS playback is sent from server to embedded playback.
- Interrupting an active turn uses a dedicated interrupt RPC.
- Stopping local playback uses a dedicated playback-control RPC.
- Server-requested local cues use a generic direct-response action RPC on
  `AudioStream`; `ServerAudioIngress` is not used for embedded playback.

This avoids overloading normal audio chunks with control semantics.

## Protobuf Ownership

`crates/proto` is the source of truth for shared gRPC contracts. Compiling either
server or embedded pulls in the generated protobuf code through the shared crate.
Protocol changes should therefore be treated as workspace-wide changes.

Package-specific gRPC details live in:

- [alia-server channel docs](../../packages/alia-server/docs/channels-and-sensors.md)
- [alia-embedded gRPC docs](../../packages/alia-embedded/docs/grpc-services.md)

## Local Development

For same-machine testing, embedded can run in local-dev binding mode and connect
to the server over localhost without completing the full binding handshake. This
is only for development and should not be used for production devices.
